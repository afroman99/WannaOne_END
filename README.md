# WannaOne_END

연주 설비(`P1-CC1-INS01`) 센서 데이터로 **24시간 안 고장 여부를 미리 알리는 조기경보** 모델을 만든다.

현재 단계: 데이터 준비, EDA, 기준 예제 재현, 전처리·특징, 평가 함수, 조기경보 모델(검증 세트 평가), 테스트 세트 예측 완료 → 팀 논의로 잠정 결정 확정 예정

## 실행 방법

### 1. 데이터 변환 (처음 한 번만)

원본 데이터 폴더(`POSKO-PdM-Data-pdm-v2.2.0`)를 받은 뒤, 프로젝트 루트에서 실행한다.

```bash
python -m src.posko_data --src <원본 폴더 경로>
```

- 원본은 해시 이름의 CSV 조각 6천여 개로 나뉘어 있다. 이 명령이 원자료 종류별 Parquet 파일 하나로 합쳐 `data/posko/`에 저장한다(약 5분, 5.4GB → 950MB).
- 행 수와 SHA-256을 원본 `manifest.json`과 대조해 검사한다.

### 2. 분석 실행

```bash
python analysis/01_eda.py
python analysis/02_baseline.py
python analysis/03_check_features.py
python analysis/04_model.py
python analysis/05_predict_test.py
```

| 스크립트 | 하는 일 | 시간 |
|---|---|---|
| `01_eda.py` | EDA 1~11절 재계산, 그림 10장 저장 | 약 20초 |
| `02_baseline.py` | 데이터셋 기준 예제 재현과 오류 분석 | 약 20초 |
| `03_check_features.py` | 전처리·특징 점검 21개 항목 (`--quick`이면 누설 검사를 표본 100개로) | 약 3분 (`--quick` 20초) |
| `04_model.py` | **메인**: 학습 세트 교차검증으로 모델·임계값 선택, 검증 세트 한 번 평가, 근거 그림 4장 | 약 1분 |
| `05_predict_test.py` | 검증한 모델로 테스트 세트 예측 → `predictions/test_risk24.csv` | 약 15초 |

- 필요한 패키지: pandas, numpy, pyarrow, matplotlib, scikit-learn (Python 3.14, pandas 3.0, scikit-learn 1.9에서 확인)
- 프로젝트 루트에서 실행한다. 그림은 `figures/`에 저장된다(저장소에는 올리지 않음).
- `05_predict_test.py`는 학습한 모델을 `models/risk24.joblib`에 저장한다(저장소에는 올리지 않음). 대시보드가 이 파일을 쓴다.
- 그래프 한글 글꼴은 `src/plotting.py`가 설치된 글꼴에서 고른다(macOS AppleGothic → Windows 맑은 고딕 → 나눔고딕). 셋 다 없으면 경고가 나오니 나눔고딕을 설치한다. 그림 파일 이름은 Windows에서도 한글이 깨지지 않게 NFC로 저장한다.
- 전처리 코드를 고치면 `03_check_features.py`를 다시 실행해 모두 통과하는지 확인한다.

## 데이터 출처

- POSKO 예측정비 **합성 데이터** `pdm-v2.2.0` (교육용 배포본). 실제 조업 데이터가 아니다. 결과는 설비 특성이 아니라 데이터 생성 규칙을 반영한다.
- 72시간짜리 독립 시나리오 360개. 시작 시각 순서로 분할돼 있다.

| 분할 | 시나리오 | 정답 | 용도 |
|---|---|---|---|
| 학습 | 216개 (`S0001`~`S0216`) | 있음 | EDA, 특징 설계, 모델·임계값 선택(교차검증) |
| 검증 | 72개 (`S0217`~`S0288`) | 있음 | 최종 평가 (한 번만) |
| 테스트 | 72개 (`S0289`~`S0360`) | 없음 | 최종 예측 |

- 사용하는 파일 (`data/posko/`, 용량 문제로 저장소에는 올리지 않음)

| 파일 | 내용 |
|---|---|
| `raw/casting.parquet` | 연주 센서 원자료 (5초 간격, 1,866만 행) |
| `raw/maintenance.parquet`, `raw/calendar.parquet` | 정비 기록, 정기수리 계획 |
| `raw/events.parquet` | 운전조건 변경 |
| `labels.parquet` | 6·24시간 고장 위험 정답 (6시간마다) |
| `diagnostics.parquet` | 상태 구간(정상·열화·고장·정비)과 원인 |
| `targets.parquet` | 잔여수명, 교체 정책 정답 |

- **지키는 규칙**
  - EDA·특징 설계·모델 선택은 학습 세트로만 한다. 검증 세트는 마지막에 한 번만 본다.
  - 정답 열과 예측 시점 이후 정보(센서·정비)는 특징으로 쓰지 않는다. `03_check_features.py`가 원자료를 예측 시점에서 잘라 다시 계산해 확인한다.
  - 검열된 정답은 0으로 채우지 않고 뺀다.

## 폴더 구성

```
  features.py        예측 시점(6시간마다)까지의 정보만으로 특징 계산, 정답 (build_dataset, FEATURE_SETS)
  evaluate.py        시점 단위 혼동행렬, 고장 단위 감지·리드타임, 비용, 임계값 선택
  model.py           비교하는 모델·특징 묶음 정의, 최종 조합(FINAL), 시나리오 단위 교차검증
  plotting.py        한글 글꼴 설정(macOS·Windows·Linux), 그림 저장

  01_eda.py          EDA: 데이터 품질, 열화 신호, 조기경보 한계, 운전조건, 센서 간 관계, 원인 구분, 정비 효과
  02_baseline.py     기준 예제(데이터셋 toolkit의 연주 예제) 재현과 오류 분석
  03_check_features.py  전처리·특징 점검 (정답, 보정값, 미래 정보 누설, 경계 상황, 손 계산, 신호 방향, 분포)
  04_model.py        메인: 조기경보 모델 선택과 검증 세트 평가
  05_predict_test.py 테스트 세트 예측 (예측 시점은 6시간마다, 정비 중인 시점 제외)

  dashboard.py       조기경보 대시보드 (추가 시도, 아래 참고)
data/posko/          변환된 데이터 (커밋하지 않음)
models/              학습한 모델 파일 (커밋하지 않음)
predictions/         테스트 세트 예측 CSV (커밋하지 않음)
figures/             번호_내용.png (커밋하지 않음, 01~10 EDA · 11 점검 · 12~15 모델)
reports/             문제정의서, 결과보고서, EDA 근거, 모델 결과 (연주_조기경보_*.md)
```

## 분석 요약

**EDA 주요 결론** (학습 세트 216개 시나리오)
- 고장은 51건이다. **점진 고장 45건**은 열화가 14.5~54.5시간 이어진 뒤 고장 나고, **돌발 고장 6건**은 신호 없이 갑자기 고장 난다. 진단 정답의 `failed` 구간만 보면 6건만 보이므로, 고장 여부는 정비 기록의 `FAILURE_DT`로 판단한다.
- 열화 신호 4개: `MLD-LVL` 진폭, `CONTROL_DELAY`, `WD-LOD`(부하 보정)는 커지고 `OSC-STK`는 작아진다. **고장 24~36시간 전부터** 정상과 갈린다.
- 24시간 앞서 잡을 수 있는 고장의 상한은 약 76%(39/51건)다.
- 네 신호를 정상 분포로 표준화한 **평균 점수**는 정상 구간의 경계 초과 비율을 5%에서 0.4%로 줄이면서 고장 전 감지 비율 79%를 유지한다.
- 센서로 고장 원인(마찰·고착·제어 지연)은 구분할 수 없다. 그래서 **원인과 상관없이 24시간 안 고장 여부**를 예측한다.
- 정비 후에도 신호가 처음 수준까지 돌아가지 않는다. 그래서 재가동 기준과 처음 수준 기준 변화량을 함께 쓴다.

**평가 기준** (잠정, 보수적 기준. 근거는 `reports/연주_조기경보_모델_결과.md` 3절)
- 원칙: 평가는 결과를 부풀리지 않게, 경보는 미탐을 줄이는 쪽으로. 비용 규칙상 고장을 놓치면 66점, 오경보는 28~48점이다.
- 모델은 학습 세트 교차검증 AP로 고르고, 임계값은 **점진 고장을 모두 잡고 진짜 오경보가 0인 임계값 중 가장 낮은 것**(오경보 없이 가장 일찍 경보)으로 정한다.
- 대표 숫자는 이른 경보도 오경보로, 돌발 고장도 놓친 것으로 센다. 비용은 원인 부품을 모른다고 보고 "두 부품 모두 교체"를 대표로 쓴다.

**조기경보 모델 결과** (검증 세트, 한 번 평가)

| | 우리 모델 | 기준 예제 (같은 규칙) |
|---|---|---|
| 모델 | 로지스틱 회귀 · 센서 + 정비 이력 특징 | 최근 12시간 요약 + 랜덤포레스트 |
| AP | **0.867** | 0.806 |
| 정밀도 / 재현율 | 0.797 / **0.843** | 0.789 / 0.800 |
| 놓친 시점 (점진 고장) | **3** | 6 |
| 고장 감지 | 14/16 (점진 14/14, 돌발 0/2) | 14/16 |
| 리드타임 중앙값 | **26시간** | 22시간 |
| 진짜 오경보 | 0 | 0 |
| 비용 (두 부품 / 최악 / 아무것도 안 함) | 812 / 1,002 / 1,056 | 852 / 1,026 / 1,056 |

- 오경보 15개는 모두 고장 24.5~38.5시간 전의 "이른 경보"다. 놓친 시점의 대부분(8개)은 신호가 없는 돌발 고장이다.
- 검증 세트의 고장은 16건뿐이라 작은 차이는 우연일 수 있다.
- **비용 효과는 원인 부품을 알 수 있느냐에 달려 있다.** 둘 중 하나를 찍어 교체하면 아무것도 안 할 때와 비용이 거의 같다.

**테스트 세트 예측** (`predictions/test_risk24.csv`)
- 검증 세트에서 평가한 모델(학습 세트로 학습, 임계값 0.76)을 그대로 쓴다.
- 예측 시점은 시나리오마다 0~66시간 6시간 간격에서 정비 중인 시점을 뺀 것이다. 이 규칙은 학습·검증 세트에서 정답 파일의 `AT_RISK=1`과 정확히 일치한다.
- 72개 시나리오, 833개 시점 중 경보 91개(10.9%), 경보가 난 시나리오 22개. 검증 세트 경보 비율(11.6%)과 비슷하다.
- 데이터셋 앱용 예측 JSON은 받은 데이터에 없는 '관측 교환본'의 해시 값이 필요해 CSV로 저장했다.

## 추가 시도: 조기경보 대시보드 (정건우)

> 팀 과제 범위 밖에서 개인적으로 추가로 해 보고 싶은 작업이다. 모델을 서비스 형태로 쓰면 어떤 모습일지 보여 주는 시연용이다.

```bash
pip install streamlit
python analysis/05_predict_test.py      # 처음 한 번: 모델 학습·저장
streamlit run app/dashboard.py          # 브라우저에서 http://localhost:8501
```

| 화면 | 내용 |
|---|---|
| 전체 현황 | 설비(시나리오)별 지금 위험 확률과 상태(경보·정상·정비 중), 위험한 순서 |
| 설비 상세 | 위험 확률과 네 신호의 흐름, 정비·고장 기록, 지금 신호 상태, 조치 안내 |
| 모델 정보 | 모델·경보 기준과 검증 세트 성능, 고장별 결과 |
| 비용 계산기 | 원인 부품을 맞힐 확률에 따른 비용 (팀 논의 항목 C). 0.68 이상 맞히면 한 부품만 바꾸는 쪽이 쌈 |

- **실시간이 아니라 재생 방식**이다. 사이드바의 '지금 시각'을 옮기면 그 시각까지의 데이터만으로 본 상태를 보여 준다.
- 저장된 모델로 예측만 한다. 특징은 예측 시점까지의 정보만 쓰므로(`03_check_features.py` 누설 검사), 실제 데이터가 들어오는 상황에서도 같은 결과가 나오는 구조다. 실시간으로 바꾸려면 `src/serving.py`의 원자료 읽기만 새 데이터로 바꾸면 된다.
- 검증 세트를 고르면 실제 고장 시각(정답)을 겹쳐 볼 수 있다. 모델은 이 정보를 보지 않는다.
