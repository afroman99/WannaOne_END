# WannaOne_END

연주 설비(`P1-CC1-INS01`) 센서 데이터로 **24시간 안 고장 여부를 미리 알리는 조기경보** 모델을 만든다.

현재 단계: 중간발표 완료(2026-10-16, git 태그 `midterm`) → 최종발표를 위한 개선·서비스화 중. 개선 1(6시간 → **1시간마다 예측**) 완료, 다음은 의사결정 지원(DSS)

## 실행 방법

### 0. 패키지 설치

```bash
pip install -r requirements.txt
```

- 확인한 버전을 고정해 두었다. 모델 파일은 만든 scikit-learn 버전에서만 같은 결과가 보장된다(버전이 다르면 대시보드가 경고한다).

### 1. 데이터 변환 (처음 한 번만)

원본 데이터 폴더(`POSKO-PdM-Data-pdm-v2.2.0`)를 강사가 제공한 구글드라이브에서 받은 뒤, 프로젝트 루트에서 실행한다.

```bash
python -m src.posko_data --src <원본 폴더 경로>
```

- 원본은 해시 이름의 CSV 조각 6천여 개로 나뉘어 있다. 이 명령이 원자료 종류별 Parquet 파일 하나로 합쳐 `data/posko/`에 저장한다(약 5분, 5.4GB → 950MB).
- 행 수와 SHA-256을 원본 `manifest.json`과 대조해 검사한다.

### 2. 분석 실행

```bash
python analysis/01_eda.py
python analysis/02_baseline.py
python analysis/03_check_features.py
python analysis/04_model.py
python analysis/05_predict_test.py
python analysis/06_caution.py
python analysis/07_cause_part.py
python analysis/08_error_analysis.py
python analysis/09_hourly.py
python analysis/10_dss_policy.py
python analysis/11_final_figures.py      # 보고서·발표용 최종 그림 22~24 (app_data/만으로)
python analysis/12_report_checks.py      # 결과보고서 피드백 확인: 같은 조건 비교, 미확정 경보 비용
python analysis/13_export_validation.py  # 원자료 없이 검산할 검증 예측·정답 CSV
```

## 데이터 출처

- POSKO 예측정비 **합성 데이터** `pdm-v2.2.0` (교육용 배포본). 실제 조업 데이터가 아니다.
- 받는 곳: 강사 제공 구글드라이브(노션으로 공유). 수강생에게만 공유된 링크라 주소는 적지 않는다. 결과는 설비 특성이 아니라 데이터 생성 규칙을 반영한다.
- 72시간짜리 독립 시나리오 360개. 시작 시각 순서로 분할돼 있다.

| 분할 | 시나리오 | 정답 | 용도 |
|---|---|---|---|
| 학습 | 216개 (`S0001`~`S0216`) | 있음 | EDA, 특징 설계, 모델·임계값 선택(교차검증) |
| 검증 | 72개 (`S0217`~`S0288`) | 있음 | 평가 전용 (모델·임계값 선택에는 쓰지 않음) |
| 테스트 | 72개 (`S0289`~`S0360`) | 없음 | 최종 예측 |

- 사용하는 파일 (`data/posko/`, 용량 문제로 저장소에는 올리지 않음)

| 파일 | 내용 |
|---|---|
| `raw/casting.parquet` | 연주 센서 원자료 (5초 간격, 1,866만 행) |
| `raw/maintenance.parquet`, `raw/calendar.parquet` | 정비 기록, 정기수리 계획 |
| `raw/events.parquet` | 운전조건 변경 |
| `labels.parquet` | 6·24시간 고장 위험 정답 (6시간마다) |
| `diagnostics.parquet` | 상태 구간(정상·열화·고장·정비)과 원인 |
| `targets.parquet` | 잔여수명, 교체 정책 정답 |

- **지키는 규칙**
  - EDA·특징 설계·모델·임계값 선택은 학습 세트로만 한다(교차검증). 검증 세트는 정해진 모델을 평가하는 데만 쓰고, 검증 결과로 모델·특징·임계값을 고르지 않는다.
  - 검증 세트를 정확히 한 번만 본 것은 아니다. 개정(모델·경보 기준 변경)과 주의 정밀도 목표 변경(0.9 → 0.85) 때 다시 평가했다. 두 번 모두 근거는 검증 숫자가 아니었고(학습 세트의 착시, 현장 대응), 바꾼 뒤 검증 숫자는 오히려 내려갔다. 그래도 검증 세트가 완전히 처음 보는 데이터는 아니다.
  - 정답 열과 예측 시점 이후 정보(센서·정비)는 특징으로 쓰지 않는다. `03_check_features.py`가 원자료를 예측 시점에서 잘라 다시 계산해 확인한다.
  - 검열된 정답은 0으로 채우지 않고 뺀다.

## 분석 요약

**EDA 주요 결론** (학습 세트 216개 시나리오)
- 고장은 51건이다. **점진 고장 45건**은 열화가 14.5~54.5시간 이어진 뒤 고장 나고, **돌발 고장 6건**은 신호 없이 갑자기 고장 난다. 진단 정답의 `failed` 구간만 보면 6건만 보이므로, 고장 여부는 정비 기록의 `FAILURE_DT`로 판단한다.
- 열화 신호 4개: `MLD-LVL` 진폭, `CONTROL_DELAY`, `WD-LOD`(부하 보정)는 커지고 `OSC-STK`는 작아진다. **고장 24~36시간 전부터** 정상과 갈린다.
- 24시간 앞서 잡을 수 있는 고장의 상한은 약 76%(39/51건)다.
- 네 신호를 정상 분포로 표준화한 **평균 점수**는 정상 구간의 경계 초과 비율을 5%에서 0.4%로 줄이면서 고장 전 감지 비율 79%를 유지한다.

- 시계열 분석: 주기(몰드 레벨 22분, 부하 18시간)는 운전 조건이고 열화 때 바뀌지 않는다. 열화는 추세(평균 점수 기울기 0 → 0.26~0.33/시간)와 변동성(몰드 레벨 진폭의 6시간 이동표준편차 약 3.9배)으로 드러나고, 누적합 변화점은 진단상 열화 시작과 거의 같은 때(중앙값 1.8시간 먼저) 잡힌다(결과보고서 4장).

**평가 기준과 팀 결정** (모두 확정)
- 원칙: 평가는 결과를 부풀리지 않게, 경보는 미탐을 줄이는 쪽으로. 비용 규칙상 고장을 놓치면 66점, 오경보는 28~48점이다.

- 대표 숫자는 이른 경보도 오경보로 센다. 재현율은 신호가 없는 돌발 고장을 빼고 점진 고장 기준으로 보고하되, 돌발 고장을 포함한 값도 함께 적는다. 원인 부품은 데이터로 알 수 없으므로 경보가 나면 "두 부품 모두 교체"한다("항상 밸브만 교체"는 944~968점으로 더 비쌈).
- 시간을 세는 특징(경과 시간, 재가동 후 시간)은 쓰지 않는다. 관측 끝 시점은 정답이 모두 "고장"이라 "오래 돌았으면 고장"이라는 착시를 배운다.

**원인 부품 구분** (`analysis/07_cause_part.py`)
- 5초 원자료의 파형 특징 182개로도 부품은 구분되지 않는다. 같은 고장 모드끼리 보면 교차검증 AUC 0.40(찍기 0.5)이고, 라벨을 섞었을 때와 차이가 없다. 전체에서 AUC가 0.64로 보인 것은 부품이 아니라 열화의 심각도를 맞힌 착시였다.
- 정비 기록에서는 "직전 정비가 부분 정비였으면 다음 고장은 그 부품"이었다(학습 6/6, 검증 2/2). 하지만 이 데이터에서는 부분 정비가 모두 하루쯤 뒤 같은 부품의 고장으로 이어진다. 현장에서는 제대로 된 부분 정비 뒤 재고장이 드물고, 재고장은 정비 불량이나 부품 불량일 때뿐이다. 그래서 합성 데이터의 성질로 보고 결정 C(두 부품 교체)는 그대로 둔다.
**남은 과제**: 지금 데이터로 할 수 있는 후속 과제는 모두 마쳤다. 실제 설비 데이터, 부품 재고·조달 기간, 현장 점검 결과가 필요한 과제는 **추후 해당 데이터가 확보되면 진행한다**(결과보고서 8장).

**화면 원칙 (콜투액션)**: 화면마다 맨 위에 **지금 할 일 하나와 주 버튼 하나**를 둔다. 데이터 세트·지금 시각·정답 보기는 오른쪽 위 **시연 설정**에 접어 두었다. 데이터 세트와 지금 시각은 옮긴 뒤 **적용**을 눌러야 바뀐다(설비관리자가 적용하면 모든 화면이 따른다). 설비 이름(예: 1연주 #06)은 시나리오 하나를 연주기 한 대로 본 가상 이름이고, 실제 이름을 쓰려면 `app/equipment_names.csv`(열: SCENARIO_ID, NAME)를 둔다.

| 보는 사람 | 화면 | 내용 |
|---|---|---|
| 작업자 | 내 작업 | 팀(정비 1팀·2팀)을 고르면 **지금 할 일 카드**: 작업명, 우선순위·진행·지연·즉시 조치·위험·부품 배지, 예정 시각, 점검 가이드. 주 버튼이 **작업 시작 → 완료 보고**(작업 결과 + 수행 내용 필수 + 점검으로 판단한 부품·확인된 원인 + **실제 조치**: 두 부품 교체·밸브만·진동장치만·교체 안 함, 지시와 다르면 이유 필수, 재고는 실제 조치대로)로 바뀐다. 현장 상황이 달라 끝내지 못하면 완료 보고 옆 **작업 중단**(사유 필수) → 설비관리자에게 알림. 즉시 조치 설비는 배정 전에도 "바로 시작". 아래 탭: 지금 · 지연 · 예정 · 완료·중단. 비용 없음 |
| 설비관리자 | 홈 · 설비 상태 | **경보 · 주의 · 정상 칸**: 칸마다 그 상태의 설비 전부를 칸 안 스크롤 목록으로(이름 · 시나리오 번호 · 24시간 내 고장 위험 · 작업 지시 상태), 칸 제목을 누르면 넓은 목록 화면 |

| 설비관리자 | 홈 · 작업 지시 현황 | **배정할 경보 칸**(누르면 배정할 시나리오 목록) · 진행 중 · 지연 · 완료 · 중단 · 정비 중, **먼저 볼 설비** 카드, 작업 목록(구분: 중단 · 지금 · 지연 · 예정 · 완료, 실제 조치와 중단·지시와 다름 사유)과 필터, 이력 CSV. 이미 시작한 작업은 예정 시각 전이라도 "지금". 중단한 설비는 다시 배정할 수 있다. **작업 수정하기**를 눌러야 작업을 골라 수정(팀·우선순위·예정·가이드·상태·완료 보고)하거나 **배정 취소**할 수 있고, 둘 다 **사유를 적어야 저장**된다 |

- **배정 = 정비 결정 승인 + 작업 지시**: 배정하면 그 팀의 작업자 화면에 나타나고, 시작·완료 보고는 판단 기록(`src/actions.py`)에도 남아 재고(완료한 교체가 부품을 씀)·온톨로지·점검 되먹임에 쓰인다.
- **화면 사용**: 화면 위치를 주소에 남겨 브라우저 뒤로·앞으로 가기가 된다. 테마는 오른쪽 위 ⋮ 메뉴에서 시스템·라이트·다크.
- **재생 시각 기준**: 작업의 배정·시작·완료·예정을 시나리오 시각(h)으로 적는다. 시각을 과거로 옮기면 그때의 작업만 보인다. 이번 운전 구간에서 교체를 마친 설비는 정비가 시작될 때까지 다시 배정 대상에 올리지 않는다(재생 데이터에는 우리가 한 교체가 반영되지 않기 때문).
- **저장**: 로컬은 `actions/tasks.sqlite3`·`actions/action_log.csv`(커밋하지 않음). 구글 로그인 + 공용 DB를 설정하면 Supabase에 남겨 노트북·폰이 같은 작업을 본다. 로그인 없는 공개 화면은 보는 사람의 세션에만 남긴다(누구나 남의 작업을 고치지 못하게).
- **현장 연동 (2차 업그레이드, 2026-10-16, 정건우)**: 설비관리자는 노트북, 작업자는 폰. 같이 보는 저장소(공용 DB·로컬 SQLite)에서는 재생 시각을 함께 쓰고(설비관리자가 바꿈), 10초마다 바뀐 것이 있을 때만 화면을 다시 그린다. 설비관리자에게는 완료 보고, 작업자에게는 새 작업 알림이 뜬다. 작업자 화면은 폰 폭에 맞췄고 홈 화면에 앱처럼 추가할 수 있다(`app/static/`).
- **발표장 대비**: 인터넷이 불안하면 `streamlit run app/dashboard.py`로 노트북을 서버로 쓰고, 같은 Wi-Fi·핫스팟의 폰이 `http://<노트북 IP>:8501`로 접속한다(로그인 없이 로컬 SQLite).
- **실시간이 아니라 재생 방식**이다. 특징은 예측 시점까지의 정보만 쓰므로(`03_check_features.py` 누설 검사) 실시간으로 옮길 수 있는 구조다.
- 1시간마다 예측하고, 한 번 켜진 경보는 정비가 시작될 때까지 경보로 유지한다. 정비 중인 설비는 경보로 세지 않는다.

## 보안과 배포

- 클라우드에는 원자료와 모델 파일을 올리지 않는다. `python -m src.app_data`로 화면에 필요한 결과만 `app_data/`(1.3MB)에 내보내고, 대시보드는 원자료가 없으면 이것만 읽는다(파일마다 SHA-256 확인).
- 팀 결정(2026-10-15): 포트폴리오용으로 저장소·대시보드 공개, 결과 업로드는 강사님 허락. 배포는 정건우가 팀 저장소를 본인 계정으로 Fork해 배포(2026-10-16 변경, 처음 결정은 팀장 계정). 공개 결정은 `deploy.toml`(`public = true`)에 남겼다. `false`로 바꾸면 비밀번호(`python -m src.auth` → Secrets `[password]`)가 있어야 열린다.
- **구글 로그인·공용 DB (선택)**: Secrets에 아래를 넣으면 등록한 구글 계정만 들어오고, 작업이 Supabase에 저장된다. 값은 저장소에 올리지 않는다(로컬은 `.streamlit/secrets.toml`, 커밋 제외).
  - `[auth]` `redirect_uri`(앱 주소 + `/oauth2callback`) · `cookie_secret` · `client_id` · `client_secret` · `server_metadata_url`(구글) — Google Cloud에서 OAuth 동의 화면(테스트 사용자 등록)과 웹 클라이언트를 만든다
  - `[db]` `url` — Supabase → Connect → Session pooler 주소 (표는 앱이 처음 접속할 때 스키마 `castpdm`에 만들고 RLS를 켠다)
  - `[users]` `managers = [이메일]`, `[users.teams]` `"정비 1팀" = [이메일]` …
  - 공용 DB 시험: `TEST_PG_URL=postgresql://… python tests/check_regression.py`
- 패키지 취약점: pip-audit 0건(tornado 6.5.9로 고정, rdflib 7.6.0 추가 후 다시 확인). 오류 상세 숨김·사용 통계 끔(`.streamlit/config.toml`). 회귀 점검 9절에 보안 항목.
- 배포: 팀 저장소를 Fork → Streamlit Community Cloud → Fork의 `main` 브랜치, 실행 파일 `app/dashboard.py` → Deploy → Settings의 Secrets에 위 값을 넣는다. 팀 저장소의 변경은 Fork에서 Sync fork를 눌러야 반영된다. 모델을 바꾸면 `05_predict_test.py` → `python -m src.app_data`를 다시 실행해 `app_data/`를 커밋한다.
