# 설계 초안 — 연주 설비 정비 의사결정지원시스템(DSS)

> 팀 논의용 초안 · 2026-10-14 · 작성: 정건우(데이터, 모델링) · **중간점검 2026-10-15 (11절)**
> 1~10절은 처음 초안 그대로 두고, 구현하면서 바뀐 것과 결과는 11절에 모았다. 숫자가 다르면 11절이 최신이다.
> 아직 정해지지 않은 것은 9절에 모았다. 숫자는 학습 세트로 계산한 값이고, 데이터에 없는 값은 **가정값**으로 따로 표시했다.

## 0. 한 줄

지금 서비스는 "이 설비가 24시간 안에 고장 날 위험이 높다"까지 알려 준다. DSS는 여기서 한 걸음 더 나가, **"그래서 언제, 무엇을, 어떻게 정비하는 게 가장 싼가"**를 선택지별 기대 비용으로 비교해 추천한다.

## 1. 왜 필요한가 — 지금 방식("경보 뜨면 바로 두 부품 교체")의 빈틈

| 빈틈 | 근거 (결과보고서) | DSS가 바꿀 결정 |
|---|---|---|
| 경보가 너무 일찍 울리면 멀쩡한 시간에 설비를 세운다 | 검증 세트 오경보 18개 중 17개가 고장 24.5~45시간 전 "이른 경보" | **언제**: 지금 세울지, 다음 계획 정지까지 기다릴지 |
| 어느 부품인지 몰라 늘 두 부품을 바꾼다 | 두 부품 교체 860점 vs 부품을 알면 500점, 손익분기 0.67 | **무엇을**: 두 부품 교체 / 점검 후 한 부품 |
| 부품이 없으면 예측해도 못 막는다 | 현장: "24시간도 부품 조달엔 빠듯", 주의는 경보보다 평균 12.4시간 먼저 | **부품**: 지금 발주해야 하는지 |
| 여러 설비가 동시에 위험하면 순서가 필요하다 | 대시보드에 72대가 동시에 나온다 | **우선순위**: 어느 설비부터 (확장) |

## 2. 지원할 결정 (추천 범위)

**1차 구현(MVP): 설비 한 대의 "정비 시점 + 방법 + 부품"**

주의나 경보가 켜진 설비를 고르면, 아래 선택지의 기대 비용과 위험을 나란히 보여 주고 하나를 추천한다.

| 선택지 | 설명 |
|---|---|
| A. 지금 바로 교체 | 설비를 세우고 두 부품 교체 |
| B. 다음 계획 정지 때 교체 | 계획 정지(가정값)까지 운전, 그때 교체. 정지 비용이 줄어든다 |
| C. 관찰 후 다시 판단 | 다음 예측(6시간 뒤)까지 운전. 주의 단계에서만 의미 있음 |
| (방법) 두 부품 / 점검 후 한 부품 | 점검으로 부품을 맞힐 확률(가정값)이 0.67을 넘으면 한 부품 쪽이 유리 |
| (부품) 재고 확인·발주 시점 | 재고가 없고 조달 기간이 고장 예상 시점보다 길면 "지금 발주" 경고 |

**2차(확장)**: 여러 설비 우선순위(정비 인력 N명 제한), 예비부품 적정 재고.

## 3. 입력

**① 모델이 주는 값 (지금 있음)**: 24시간 고장 확률, 지금 열화 중일 확률, 단계(정상·주의·경보), 네 신호 점수.

**② 데이터로 근거를 댈 수 있는 값: 단계별 "몇 시간 안에 고장 날 확률"**

모델은 24시간 확률 하나만 준다. 선택지마다 "그 시점까지의 고장 확률"이 필요하므로, 학습 세트 교차검증 예측에서 단계별 실제 고장 비율을 구했다(초기 추정).

| 지금 단계 | 6시간 안 | 12시간 안 | 24시간 안 | 48시간 안 | 고장까지 남은 시간 (중앙값) |
|---|---|---|---|---|---|
| 경보 (215개 시점) | 0.21 | 0.44 | 0.80 | (1.00) | 13.5시간 |
| 주의, 경보 아님 (173개) | 0.00 | 0.00 | 0.12 | (0.87) | 35.0시간 |
| 정상 (1,531개) | 0.00 | 0.01 | 0.02 | (0.08) | 39.2시간 |

- 계산: 그 시간 안에 같은 운전 구간에서 고장이 났는지를 센다. 관측이 끝났거나 다른 정비가 끼어 결과를 알 수 없는 시점은 뺀다.
- **48시간 값은 괄호로 둔다.** 관측이 72시간뿐이라 결과를 알 수 있는 시점이 고장 난 쪽으로 치우친다. 실제보다 높게 나올 가능성이 크다.
- 읽는 법: 경보가 떴어도 **6시간 안에 고장 날 확률은 0.21**이다. 그래서 "다음 계획 정지까지 기다리기"가 싼 경우가 생긴다. 주의 단계는 **24시간 안 0.12**라 대부분 점검·발주로 충분하다.

**③ 가정값 (데이터에 없음, 화면에서 바꿀 수 있게)**

| 가정값 | 기본값(안) | 쓰는 곳 |
|---|---|---|
| 다음 계획 정지까지 남은 시간 | **데이터에 있음**: `calendar` 표(정기 부품 교체 계획, 연주 30건 = 실제 정기 교체 30건과 시작 시각 일치). 계획은 미리 안다고 **가정** | 선택지 B |
| 계획 정지 중 교체 시 정지 비용 | 0 (이미 서 있으므로) | 선택지 B |
| 부품 재고 (밸브·진동장치) | 각 1개 | 부품 경고 |
| 부품 조달 기간 | 24시간 | 부품 경고 |
| 점검으로 부품을 맞힐 확률 | 0.5 (모름) | 방법 비교 |
| 점검 비용 | 데이터셋 부분 정비 기준 9점 | 방법 비교 |

## 4. 의사결정 엔진

**비용식 (강사 안내와 같은 틀, 데이터셋 비용 규칙 사용)**

> 기대 총비용 = 정비 비용 + 정지(생산 차질) 비용 + P(그 시점까지 고장) × 고장 시 손실

| 항목 | 값 (데이터셋 규칙, 점수) |
|---|---|
| 한 부품 교체 | 부품 12 + 정지 4시간 × 2 = 20 |
| 두 부품 교체 (지금 방식) | 부품 12 × 2 + 정지 8 + 멀쩡한 부품 하나의 불필요 정비 8 = 40 (`src/evaluate.py`의 `PART_RULES`와 같음) |
| 계획 정지 중 교체 | 위에서 정지 비용 8을 뺀 값 (계획 정지 중 정지 비용은 가정값) |
| 고장 | 복구 30 + 정지 8시간 × 2 + 고장 벌점 20 = 66 |
| 불필요 정비 | 8 |

- P(그 시점까지 고장)은 3절 ② 표에서 단계와 기다리는 시간으로 고른다.
- **안전 규칙이 비용보다 먼저**: 경보이고 6시간 안 고장 확률이 높은 구간(예: 확률 0.9 이상, 또는 네 신호 점수가 기준 이상)이면 비용과 상관없이 "즉시 정지"로 고정한다. 기준값은 팀이 정한다.
- 출력: 추천 선택지, 선택지별 기대 비용 표, **근거 문장**("경보지만 6시간 안 고장 확률 0.21, 계획 정지가 6시간 뒤라 기다리면 기대 비용 X점 낮음"), 그리고 가정값이 바뀌면 추천이 뒤집히는 경계(민감도).
- 판단은 계산과 규칙으로만 한다. 생성형 AI는 쓰더라도 설명 문장 작성 보조로만 쓴다(확장 아이디어).

## 5. 화면 (대시보드에 "의사결정" 화면 추가)

1. 설비 고르기 (지금 주의·경보인 설비가 위로)
2. 지금 상태: 단계, 확률, 신호 (설비 상세 화면과 같은 정보)
3. 가정값 패널: 3절 ③을 슬라이더·입력칸으로
4. 선택지 비교 표: 기대 비용, 고장 위험, 정지 시간 → 추천 강조
5. 근거와 경고: 안전 규칙 적용 여부, 부품 발주 경고, "이 가정이 바뀌면 추천이 바뀐다"

## 6. 서비스 뼈대 — 온톨로지 기반

DSS 계산(4절)과 화면(5절)을 **"객체·링크·액션"으로 짠 하나의 데이터 구조(온톨로지)** 위에 올린다. 지금은 모델 결과, 정비 이력, 비용 규칙이 파일과 함수에 흩어져 있다. 온톨로지로 묶으면 "경보 → 어느 설비 → 어느 부품 → 재고 → 정비 결정"을 한 줄로 따라갈 수 있다.

> 온톨로지는 모델 정확도를 올리지 않는다. 바꾸는 것은 **결과를 쓰는 방식**(연결, 설명, 되먹임)이다.

**① 객체 (무엇이 있나)**

| 객체 | 데이터 출처 | 주요 속성 | 상태 |
|---|---|---|---|
| 설비 | `equipment` | 설비 ID(P1-CC1-INS01), 공정, 지금 단계 | 있음 |
| 부품 | `parts`, `replacements` | 부품 코드·이름(밸브, 진동장치), 재고, 조달 기간 | 재고·조달은 **가정값** |
| 신호 | `casting` (1시간 요약) | 몰드 레벨 진폭, 제어 지연, 인발 부하, 진동 스트로크, 네 신호 점수 | 있음 |
| 예측 | 우리 모델 | 24시간 고장 확률, 열화 확률, 단계, 예측 시각 | 있음 |
| 경보 | 대시보드 | 주의(CAUTION) / 경보(WARNING), 처음 켜진 시각 | 있음 |
| 정비 작업 | `maintenance` | 작업 지시 번호, 유형(점검·부분·수리·교체), 정지 시간, 비용 점수 | 있음 |
| 고장 | 정답 라벨 (학습·검증만) | 고장 시각, 원인 부품 | 서비스에서는 사후 기록 |
| 정비 결정 | DSS (4절) | 추천 선택지, 선택지별 기대 비용, 근거 문장, 안전 규칙 적용 여부 | **새로 만듦** |
| 슬래브·생산 흐름 | `casting`의 `SLAB_NO`, `flow/` | 다음 공정(용접, 소둔, 조질압연)으로 이어지는 작업과 품질 | 확장 |

**② 링크 (어떻게 이어지나)**

| 링크 | 근거 |
|---|---|
| 설비 —가진다→ 부품 | `parts` 표 |
| 신호 —관측한다→ 설비 | `casting`의 `EQP_CD` |
| 예측 —대상→ 설비, 예측 —근거→ 신호 | 모델 입력 |
| 경보 —근거→ 예측 | 임계값 0.67 / 0.38 |
| 경보 —요청한다→ 정비 결정 | DSS |
| 정비 결정 —실행된다→ 정비 작업 —교체한다→ 부품 | `maintenance`, `replacements` |
| 고장 —원인→ 부품 | 정답 라벨 (사후) |
| 슬래브 —만들어졌다→ 설비, 슬래브 —다음 공정→ 생산 흐름 | `flow/operations` (확장) |

- **"신호 → 부품" 링크는 넣지 않는다.** 분석에서 센서로는(5초 원자료로도) 고장 부품을 구분하지 못했다(결과보고서 부록 A의 E9, 원인 맞힘 0.35~0.42 = 찍기 0.37). 이 링크를 그려 두면 근거 없는 추론을 부른다. 현장 지식으로 넣는다면 **가정**으로 표시한다.

**③ 액션 (사람이 화면에서 하는 일 → 다시 데이터로)**

| 액션 | 누가 | 바뀌는 객체 |
|---|---|---|
| 정비 결정 승인 / 보류 | 정비 책임자 | 정비 결정 → 정비 작업 생성 |
| 부품 발주 | 자재 담당 | 부품 재고·입고 예정 |
| 점검 결과 입력 (어느 부품이 문제였나) | 정비원 | 정비 작업, 고장 원인 부품 |

- **되먹임 고리**: 점검 결과가 쌓이면 지금 가장 큰 빈틈인 "어느 부품인지 모른다"를 데이터로 풀 수 있다. 쌓인 기록으로 "점검으로 부품을 맞힐 확률"을 추정하고, 이 값이 손익분기 0.67을 넘는 순간 DSS 추천이 "두 부품 교체"에서 "점검 후 한 부품"으로 바뀐다.
- 액션 기록은 프로토타입에서는 로컬 파일(CSV)에 쌓는다.

**④ 구현 방식 (안)**

| 방식 | 내용 | 장점 | 부담 |
|---|---|---|---|
| **가벼운 방식 (추천)** | `src/ontology.py`에 객체·링크·액션을 정의하고, 기존 표를 객체로 읽어 온다 | 새 설치 없음, 지금 코드·대시보드에 바로 붙음 | 형식 추론기는 없음 |
| OWL/RDF | rdflib + SPARQL로 짓고 Protégé로 그림 | 표준 "온톨로지"로 설명하기 쉬움 | 설치·학습 시간 |
| 그래프 DB (Neo4j) | 서버에 그래프 저장 | 큰 그래프에 강함 | 설비 1종·부품 2개 규모에는 과함 |

- **팀 결정 12 (2026-10-15): OWL/RDF로 구현**했다. 스키마는 `ontology/casting_dss.ttl`, 인스턴스와 SPARQL 질의는 `src/ontology.py`, 대시보드의 "근거 따라가기"에서 쓴다. ③ 액션(승인·보류·부품 발주·점검 결과)과 되먹임도 `src/actions.py`로 구현했다. 결과보고서 11-3절 참고.
- 팀원 모델(6시간 위험)은 같은 "예측" 객체에 속성 하나로 붙이면 되므로, 두 모델 통합이 오히려 쉬워진다.
- **LLM 확장(10절)과 이어진다**: "왜 이 설비를 지금 세우라는 거야?"라고 물으면 링크를 따라가며 근거(예측 → 신호 → 비용 → 안전 규칙)를 답한다. 판단은 여전히 4절의 계산과 규칙이 하고, LLM은 설명만 한다.

## 7. 성과를 어떻게 보여 주나 — 세 정책 비교 시뮬레이션

같은 데이터, 같은 모델 예측으로 세 정책을 돌려 **실제 고장 시각으로 채점**한다.

| 정책 | 규칙 |
|---|---|
| ① 정기 교체만 | 데이터에 있던 정기 교체만 수행 ("아무것도 안 함"에 해당) |
| ② 경보 즉시 교체 (지금) | 경보가 뜨면 바로 두 부품 교체 |
| ③ DSS | 4절 엔진의 추천대로 수행 |

- 지표: 기대 총비용, 고장 횟수, 정비 횟수, 설비 정지 시간, 안전 규칙 발동 횟수.
- 정책의 기준값(안전 규칙 기준 등)은 **학습 세트로만** 정하고, 검증 세트에서 한 번 비교한다(지금까지의 원칙).
- 계획 정지 일정은 `calendar` 표의 정기 교체 계획을 쓴다(미리 안다고 가정). 계획이 없는 시나리오는 "계획 없음"으로 둔다.
- 모델 평가(AP, 리드타임, 오경보)와 비용 평가는 나눈다. **비용은 이 시뮬레이션의 정책 비용으로 계산한다.** 지금 보고서의 비용(860점)은 정책 ②만 계산한 값이다.
- 근거(2026-10-15, 1시간 예측 실험): 1시간 예측 모델은 검증 세트에서 정책 ② 비용이 1,020점으로 올랐다. 늘어난 경보 묶음 4개 중 3개가 정기 교체 1~9시간 전의 맞는 경보(S0248·S0254·S0257), 1개가 경보 깜빡임(S0233)이었기 때문이다. 정책 ③이라면 "예정 교체 때 함께"로 추가 비용 없이 처리된다.
- 결과는 반드시 **"시뮬레이션에 따른 예상 절감액"**으로 표현한다.

## 9. 팀이 정할 것

1. **범위**: 1차를 "정비 시점 + 방법 + 부품"으로 할지, 우선순위를 먼저 할지
2. **가정값 기본값**: 계획 정지 간격, 재고, 조달 기간, 점검으로 부품을 맞힐 확률 (현장 경험 근거가 있으면 가장 좋다)
3. **안전 규칙 기준**: 어떤 조건이면 무조건 즉시 정지인가
4. **역할**: 구현 담당 1명과 나머지 담당
5. **팀원 모델의 활용**: 6시간 위험 예측을 "6시간 안 고장 확률"의 다른 근거로 쓸지 (지금 표의 경보 단계 0.21과 비교)
6. **온톨로지 형태**: 6절 ④의 가벼운 방식으로 갈지, OWL/RDF 같은 형식 온톨로지로 갈지 (강사 안내에서 말한 "온톨로지"가 어느 쪽인지 확인)

## 10. 확장 아이디어 (발표 마무리용)

- 여러 설비 우선순위, 예비부품 적정 재고, 정비 인력 배치
- 현장 점검 결과가 쌓이면 "점검으로 부품을 맞힐 확률"을 데이터로 추정
- 온톨로지에 다른 설비(소둔, 배풍기 등)를 객체로 더해 공장 전체로 넓히고, 연주 고장이 다음 공정 품질에 주는 영향을 생산 흐름 링크로 추적
- 생성형 AI로 근거 설명과 가정값 입력을 돕고, 다른 설비·다른 데이터 형식에도 붙일 수 있게 확장
